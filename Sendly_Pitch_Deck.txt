EXECUTIVE SUMMARY:
Sendly is a serverless, peer-to-peer crypto gifting protocol engineered natively
for the BOT blockchain ecosystem. Built with pure Solidity (^0.8.24) and
OpenZeppelin 5.x security primitives, Sendly solves Web3 onboarding and peer-to-peer
crypto gifting by eliminating the requirement to know a recipient's address beforehand.

A sender locks native BOT onchain, selects the number of recipients (1–100 slots),
and sets an expiration time. A link is generated containing a client-side ephemeral
private key in the URL fragment (#). When a recipient clicks the link, their browser
locally signs an EIP-191 digest binding the claim to their own address, preventing
mempool front-running. The smart contract distributes equal shares with zero dust loss,
and the sender can trustlessly reclaim any unclaimed funds once expired.

No backend, no database, no custodian, and zero protocol fees.

SLIDE 2: THE PROBLEM - ONBOARDING & CRYPTO GIFTING FRICTION
--------------------------------------------------------------------------------
Web3 transactions require knowing the recipient's public address before sending,
creating substantial barriers for social gifting, tipping, and onboarding:

1. The Address Prerequisite Barrier:
   - Senders cannot give crypto to newcomers who don't yet have a wallet address.
   - Traditional crypto transfers require back-and-forth messaging ("What's your address?"),
     destroying spontaneous gifts, rewards, and viral community giveaways.

2. Custodial & Off-Chain "Red Packet" Vulnerabilities:
   - Existing social tipping bots (Telegram/Discord bots, WeChat red packets) rely on
     centralized servers holding users' funds, custodying private keys, and collecting KYC.
   - Centralized tipping bots are frequently hacked, shut down, or deplatformed.

3. Mempool Front-Running & Link Theft:
   - Simple voucher links or private-key links posted in public chats get instantly
     swept by automated MEV bots scanning the mempool or message logs.

4. Stuck Funds & Dust Fragmentation:
   - Existing gift contracts leave fractional "dust" behind due to integer division,
     or permanently lock unclaimed funds when recipients fail to claim before expiration.

--------------------------------------------------------------------------------
SLIDE 3: THE SOLUTION - SENDLY
--------------------------------------------------------------------------------
Sendly provides an elegant, 100% decentralized architecture for link-based gifting:

- Send BOT with a Link:
  Gifting is as simple as sharing a URL via Telegram, WhatsApp, Discord, X, or email.

- Client-Side Signer in URL Fragment:
  The frontend generates an ephemeral private key in the user's browser (viem).
  Only the corresponding public address is committed to the blockchain. The private
  key lives strictly in the URL fragment (`#/claim/<id>/<key>`), which browsers never
  transmit to any web server.

- Cryptographic Front-Running Immunity (EIP-191):
  To claim, the recipient signs `computeDigest(packetId, msg.sender)` using the key
  from the link. Because `msg.sender` is hardcoded into the cryptographic digest,
  a copied signature or intercepted payload is mathematically useless to anyone else.

- Dust-Free Remainder Handling:
  The contract calculates `amount = total / slots`. The final claimer automatically
  receives all remaining balance, ensuring 100% of the locked BOT is distributed.

- Trustless Sender Reclaim:
  If a packet expires with unclaimed slots, the original creator can reclaim the
  exact remaining balance with a single click.

SLIDE 4: SMART CONTRACT ARCHITECTURE & PROTOCOL DESIGN
--------------------------------------------------------------------------------
Core Protocol Design (`Sendly.sol`):

   [ Sender ]                      [ Sendly Smart Contract ]               [ Claimer ]
       |                                      |                                 |
   1. Generate ephemeral key locally          |                                 |
   2. createPacket{value}(signer, slots, ...) |                                 |
       |------------------------------------->|                                 |
       |                                      |                                 |
       |  Share URL: #/claim/<id>/<key>       |                                 |
       | - - - - - - - - - - - - - - - - - - - - - - - - - - - - - - - - - - - >|
       |                                      |                                 |
       |                                      |  3. Compute EIP-191 digest      |
       |                                      |  4. Sign digest with key locally|
       |                                      |  5. claim(id, signature)        |
       |                                      |<--------------------------------|
       |                                      |                                 |
       |                                      |  6. Recover signer via ECDSA    |
       |                                      |  7. Verify msg.sender in digest |
       |                                      |  8. Transfer BOT share directly |
       |                                      |-------------------------------->|
       |                                      |                                 |
   9. (If expired) reclaim(id)                |                                 |
       |------------------------------------->|                                 |
       |  Refunds remaining BOT               |                                 |
       |<-------------------------------------|                                 |

Technical Specifications:
- Language & Framework: Solidity ^0.8.24, Foundry
- Dependencies: OpenZeppelin 5.0.2 (`ReentrancyGuard`, `ECDSA`, `MessageHashUtils`)
- Gas Optimizations: Custom errors only, unchecked counters where safe, minimal storage
- Security Features: Non-reentrant, checks-effects-interactions, zero admin, no fee,
  no proxy/upgradeability, direct caller payouts.
- Test Suite: 21 passing Foundry tests (unit tests, front-running tests, reentrancy
  tampering tests, 256-run fuzz tests, and 640-call stateful invariant tests).
